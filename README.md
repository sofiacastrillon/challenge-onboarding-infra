# Challenge Onboarding Infrastructure

AWS CDK (TypeScript) stack that creates the data and messaging resources for the Training service of `challenge-onboarding-sofia`. The Lambdas, the HTTP API and their permissions live in the companion repository `challenge-onboarding-backend`.

- Account and region: set through `.env` (`AWS_ACCOUNT_ID`, `AWS_REGION`).
- Stage: `training` in the current deployment.
- Stack name: `challenge-onboarding-sofia-infra-<STAGE>`.

## Resources

The stack `InfrastructureStack` builds these resources:

| Resource | Name in AWS | Used by |
| --- | --- | --- |
| DynamoDB table | `challenge-onboarding-sofia-training-<STAGE>` (`pk`, `sk`, pay per request) | Training Lambdas (agent, HubSpot webhook, conversations) |
| SNS topic | `challenge-onboarding-sofia-training-<STAGE>` | Training events published by the backend |
| SQS queue | `challenge-onboarding-sofia-training-<STAGE>` (visibility timeout 60 s) | SQS to Kafka Lambda |
| SQS dead-letter queue | `challenge-onboarding-sofia-training-dlq-<STAGE>` (14-day retention) | Messages that fail 3 times (`maxReceiveCount: 3`) |
| SNS subscription | Topic to queue, with `rawMessageDelivery` | Forwards every training event to the queue |
| SNS topic (example) | `challenge-onboarding-sofia-example-entity-<STAGE>` | Left over from the skeleton; no backend code publishes to it |

Not created by this stack, even though the template has keys for them: the Examples and Outbox DynamoDB tables (`DynamoTableKeys`), the MySQL cluster (commented out in `stacks/mysql/index.ts`), and the S3 bucket (commented out in `stacks/s3/index.ts`). Kafka is not created here: the topic lives in Confluent Cloud, and its credentials are in SSM (see below).

Stage behaviour, from `TrainingTable.ts`:

- The table is destroyed when the stack is destroyed, unless the stage is `production` or `testing`.
- Point-in-time recovery is enabled only for `production`.

## Outputs

The stack exports these values with CloudFormation. The backend reads them with `Fn.importValue` (`stacks/utils/Utils.ts`, using `OutputEnvMap` in `layers/common/shared/domain/interfaces/IEnvironment.ts`):

- `challenge-onboarding-sofia-training-name` and `challenge-onboarding-sofia-training-arn` (DynamoDB table)
- `challenge-onboarding-sofia-training-topic-arn` (SNS topic)
- `challenge-onboarding-sofia-training-queue-arn` and `challenge-onboarding-sofia-training-queue-url` (SQS queue)
- `challenge-onboarding-sofia-training-dlq-queue-arn` and `challenge-onboarding-sofia-training-dlq-queue-url` (DLQ)

Names are generated by `generateOutputName` in `utils/utils.ts`. Export names do not include the stage, so a second stage in the same account and region would collide with these exports. If you rename a resource, the backend fails at deploy time until both stacks agree.

## Secrets

Nothing secret is stored in this repository or created by CDK. These SecureString parameters in SSM are created by hand and read by the backend:

- `/challenge-onboarding-sofia/hubspot/webhook-secret`
- `/challenge-onboarding-sofia/confluent/api-key`, `api-secret`, `sr-api-key`, `sr-api-secret`
- `/challenge-onboarding-sofia/agent/api-key`

## Getting started

Requirements: Node.js 24 (`.nvmrc` pins v24.11.1), AWS CDK CLI compatible with `aws-cdk-lib` 2.236.0, and AWS CLI signed in to the target account (`aws sso login`).

```bash
npm install
```

Create `.env` in the repository root:

```dotenv
STAGE=training
AWS_ACCOUNT_ID=<your-12-digit-account-id>
AWS_REGION=us-east-1
```

All three variables are required. `index.ts` fails before creating the stack if one is missing.

### Commands

- `npm run build`: compile TypeScript.
- `npm run synth`: synthesize the CloudFormation template.
- `npm run diff`: compare the stack with what is deployed.
- `npm run deploy`: run `cdk deploy --all`. Run it only when infrastructure changes; the backend does not need it for code changes.
- `npm run destroy`: run `cdk destroy --all`. In `training` this deletes the table and its data.
- `npm run lint`: run ESLint and `tsc --noEmit`. The pre-commit hook runs `npm run lint`.

There are no test suites in this repository yet.

## Conventions

### Names

`index.ts` sets two constants:

```typescript
export const PROJECT_NAME = 'challenge-onboarding-sofia';
export const STACK_NAME = 'challenge-onboarding-sofia-infra';
```

- `PROJECT_NAME` must match `PROJECT_NAME` in the backend (`stacks/constants.ts`). The backend uses it to find these resources by name.
- `STACK_NAME` must be different, so it does not collide with the backend stacks.

### Tags

`utils/tags.ts` applies these tags to the stack: `ProjectName`, `Project`, `Repository`, `IsCritical`, `IsTemporal`, `Environment`, and `Owner`. Empty values are skipped. The values come from the tags object built in `index.ts`.

### Stages

`interfaces/IStages.ts` defines only `production` and `testing`. The current deployment uses `training`, which is not in that enum, so it gets the destroy-on-delete behaviour and no point-in-time recovery. Stage names are used in resource names, so renaming a stage creates new resources.

### Adding a resource

1. Create a class with a static `build` method in the right directory (`stacks/<service>/`).
2. Add its key to the matching enum in `interfaces/`.
3. Call its `build` from `stacks/<service>/index.ts`, and add the output in the same file.
4. If the backend reads it, export the name and tell the backend repository.

## Security

- No credentials or ARNs are hardcoded. Account and region come from `.env`.
- Secrets are SecureString parameters in SSM, created by hand.
- Use least privilege. Table and topic permissions are granted to the backend Lambdas in the backend stack, not here.
